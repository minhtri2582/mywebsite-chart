🧑‍💼 Interviewer:
Can you explain some common deployment strategies like blue/green and canary deployments?

🧑‍💻 Candidate (You):
Sure. These are strategies to reduce downtime and risk during deployment:
•	Blue/Green Deployment:
You maintain two identical environments — Blue (current live) and Green (new version). You deploy to Green, test it, then switch traffic over using a load balancer. If something fails, rollback is easy — just switch back to Blue.
•	Canary Deployment:
You gradually release a new version to a small subset of users. If no issues occur, you incrementally roll it out to more users. It’s useful for monitoring real-world behavior and minimizing impact from bugs.

🧑‍💼 Interviewer:
How do you package applications for deployment?

🧑‍💻 Candidate:
I typically containerize applications using Docker, regardless of language or framework. Here’s how I usually handle it:
•	Node.js:
Use npm run build to prepare production artifacts, then create a Docker image from that:

FROM node:18-alpine
WORKDIR /app
COPY . .
RUN npm ci && npm run build
CMD ["node", "dist/main.js"]


	•	Java/Gradle:
Use gradle build to create a .jar file, then:

FROM openjdk:17
COPY build/libs/app.jar /app/app.jar
CMD ["java", "-jar", "/app/app.jar"]



These Docker images are then pushed to a container registry (like ECR or Docker Hub) for deployment.

🧑‍💼 Interviewer:
Can you describe your typical CI/CD deployment workflow?

🧑‍💻 Candidate:
Yes, it usually looks like this:
1.	Code pushed to Git (feature, develop, or release branch)
2.	CI pipeline triggers:
•	Linting, unit tests
•	Build artifact (e.g., Docker image, .jar, static site)
•	Push to registry (ECR, Artifactory)
3.	CD pipeline triggers:
•	Deploy to a lower environment (e.g., Dev, QA)
•	Run integration tests or health checks
•	Deploy to production using blue/green or canary (based on approval gates)

I use Jenkins, GitHub Actions, or GitLab CI, depending on the organization.

🧑‍💼 Interviewer:
How do you manage branching models and the release process?

🧑‍💻 Candidate:
I follow Git Flow or a simplified variant:
•	main: Stable production code
•	develop: Ongoing development
•	feature/*: Individual features
•	release/*: Pre-production, QA testing
•	hotfix/*: Urgent patches to main

We use PRs with code reviews and approvals before merging. Each release is tagged with a semantic version (e.g., v1.2.3), and CI pipelines are configured to deploy tagged versions to production.

For release visibility, we maintain a changelog and often include release notes with Jira integration.

🧑‍💼 Interviewer:
What challenges have you faced in CI/CD and how did you overcome them?

🧑‍💻 Candidate:
A few examples:
•	Slow pipelines: Solved with build caching, parallel steps, and caching Docker layers.
•	Flaky tests: Flagged and isolated unstable tests; integrated retry logic and test coverage reports.
•	Secrets management: Replaced inline secrets with tools like AWS Secrets Manager or Vault and used CI tool integration for secure injection.
•	Rollback strategy: Implemented automated rollback using health checks + Terraform/CD pipelines in blue/green deployment models.
